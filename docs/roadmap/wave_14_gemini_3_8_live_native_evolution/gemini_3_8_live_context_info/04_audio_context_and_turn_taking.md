## 1. Введение: Почему в Gemini Live аудио — это полноправный контекст

В традиционных каскадных конвейерах (ASR $\to$ LLM $\to$ TTS) звук никогда не являлся контекстом нейросети. Модель оперировала исключительно распознанным текстом, а детектор пауз (VAD) работал автономно по порогу громкости в децибелах.

В нативных мультимодальных моделях **Gemini 3.8 Live** и **Gemini 3.8 Live Extended Thinking** аудиопоток оцифровывается и преобразуется энкодером в **непрерывные токены внимания (аудиоэмбеддинги)**. Звуковой тракт находится в общем KV-кэше трансформера наряду с системным промптом, историей диалога и скрытыми рассуждениями (CoT).

Из этого фундаментального факта вытекают четыре системных инварианта контекста:
1. **Аудио выжигает контекстное окно:** звук расходует токены непрерывно, вытесняя ранние данные из скользящего окна (`SlidingWindow compression`).
2. **Переход диалоговой инициативы (Turn-Taking) управляется смыслом:** завершение реплики — это расчет совместного распределения акустических и смысловых векторов.
3. **Прерывание (Barge-In) физически обрезает контекст модели:** при встречном голосе сервер обрезает сгенерированный ход ассистента до последнего байта.
4. **Акустическое эхо уничтожает контекст:** если несинхронизированный звук динамика попадает в микрофон, модель фиксирует перебивание и преждевременно кастрирует собственную генерацию.

## 2. Семантический VAD в мультимодальном пространстве внимания

Вероятность завершения фразы пользователем ($P(\text{TurnComplete})$) вычисляется трансформером на каждом аудиофрейме как совместная функция акустики и накопленного контекста диалога:

$$P(\text{TurnComplete} \mid X_{\le t}, C) = \sigma\left(\mathbf{W}_{\text{turn}} \cdot \text{SelfAttention}\left(Q(X_t), K([X_{<t}, C]), V([X_{<t}, C])\right)\right)$$

где:
- $X_t$ — текущий фрейм звука (PCM 16 кГц);
- $X_{<t}$ — предшествующие аудиоэмбеддинги текущей фразы;
- $C$ — синтаксический, прагматический и фактологический контекст сессии.

### 2.1. Механика смыслового подавления пауз
- **Незавершенная мысль:** если пользователь замолкает на полуслове или после союза («Мы подняли реплику базы данных, но...»), семантический контекст $C$ проецирует высокую вероятность продолжения фразы. Это **подавляет передачу хода даже при физической тишине длительностью до 800–1200 мс**.
- **Завершенная мысль:** если фраза синтаксически завершена («...и поэтому упал коннект-пул») и сопровождается интонационным спадом тона, модель фиксирует границу хода уже через **200–300 мс** тишины.

## 3. Аномалия бесконечного поглощения PCM и калибровка VAD

> [!WARNING]
> **Критическая серверная аномалия Gemini 3.8 Live:**  
> В отличие от `gemini-3.1-flash-live`, стабильно эмитировавшего событие `ACTIVITY_START` через 200 мс после начала речи, модель `gemini-3.8-live` при непрерывном стриминге сырого PCM с параметрами по умолчанию способна бесконечно накапливать аудиоданные в контекстном буфере без перехода к синтезу ответа.

Для устранения этой аномалии обязательна жесткая калибровка параметров структуры `realtimeInputConfig.automaticActivityDetection` в стартовом сообщении `setup`:

| Параметр (`camelCase`) | Калиброванное значение | Влияние на контекст и диалоговый автомат |
| :--- | :--- | :--- |
| `disabled` | `false` | Серверный нативный VAD активен. (При `true` требуется ручная оркестрация). |
| `startOfSpeechSensitivity` | `"START_SENSITIVITY_LOW"` | Игнорирует шум вентиляторов, дыхание и шорохи, предотвращая ложные старты контекста. |
| `prefixPaddingMs` | `200` | Сохраняет 200 мс аудио до точки детекции, защищая первый слог от обрезания. |
| `endOfSpeechSensitivity` | `"END_SENSITIVITY_LOW"` | Предотвращает ложную фиксацию конца фразы во время пауз размышления. |
| `silenceDurationMs` | `500` | Оптимальное окно тишины (500 мс). Ниже 300 мс — режет фразы, выше 800 мс — создает задержку. |
| `activityHandling` | `"START_OF_ACTIVITY_INTERRUPTS"` | Полнодуплексный режим: входящий голос человека немедленно прерывает речь модели. |

```json
{
  "setup": {
    "model": "models/gemini-3.8-live",
    "realtimeInputConfig": {
      "automaticActivityDetection": {
        "disabled": false,
        "startOfSpeechSensitivity": "START_SENSITIVITY_LOW",
        "prefixPaddingMs": 200,
        "endOfSpeechSensitivity": "END_SENSITIVITY_LOW",
        "silenceDurationMs": 500
      },
      "activityHandling": "START_OF_ACTIVITY_INTERRUPTS"
    }
  }
}
```

## 4. Срез контекста при прерывании (Barge-In) и гонка опустошения ЦАП (DAC Drain)

### 4.1. Физическая модификация KV-кэша при `interrupted: true`
Когда пользователь перебивает ассистента во время генерации речи:
1. Серверный VAD мгновенно детектирует встречный звук и отправляет пакет `serverContent { interrupted: true }`.
2. Инфраструктура инференса Google **физически обрезает сгенерированную реплику модели в контекстном KV-кэше до того токена, на котором прозвучало прерывание**.
3. Все последующие рассуждения и недосказанные фразы стираются из памяти. Модель помнит ровно то, что успела фактически произнести.

### 4.2. Ловушка опустошения ЦАП (Петля самопрерывания и самокастрации контекста)
Гонка состояний между сетевым сокетом и физическим выводом звука динамика — главная причина разрушения контекста в голосовых интерфейсах:

```
t = 0 мс:        Сервер закончил генерацию текста и прислал сетевой пакет:
                 serverContent { turnComplete: true }
t = 20 мс:       Клиент получил пакет turnComplete. Если в этот момент переключить
                 UI в режим «Слушаю» и открыть микрофон на прием звука...
t = 20–450 мс:   В аппаратном аудиобуфере и ЦАП еще звучит громкий хвост фразы модели!
                 Звук из динамиков попадает в микрофон -> Эхо ->
                 Серверный VAD слышит голос -> Считает, что пользователь перебил ассистента ->
                 Сервер шлет serverContent { interrupted: true } ->
                 Контекст завершенного ответа модели ОБРЕЗАЕТСЯ, мысль стирается из KV-кэша.
```

### 4.3. Математический инвариант готовности к приему реплики ($T_{\text{drain}}$)
Клиентский контроллер имеет право переключить статус диалога в ожидание ответа пользователя ($S = \text{LISTENING}$) и активировать микрофон **только после физического затихания звука в динамиках**:

$$T_{\text{drain}} = t_{\text{ctx}} + \frac{N_{\text{unplayed}} + N_{\text{hardware}}}{f_s}$$

где:
- $t_{\text{ctx}}$ — системное время аудиоконтекста (`currentTime`);
- $N_{\text{unplayed}}$ — количество сэмплов, ожидающих воспроизведения в буфере;
- $N_{\text{hardware}}$ — аппаратная задержка драйвера ОС (`outputLatency + baseLatency`);
- $f_s = 24\,000\text{ Гц}$ — частота дискретизации синтеза модели.

Диалоговый автомат ожидает интервал:
$$\Delta t_{\text{wait}} = \max\left(0, \, T_{\text{drain}} - t_{\text{ctx}}\right) \equiv 0$$

## 5. Протокольные антипаттерны управления контекстом через аудио

Попытки управлять диалогом с помощью искусственных манипуляций со звуковым потоком приводят к фатальным сбоям сессии.

### 5.1. Антипаттерн `audioStreamEnd: true` в роли терминатора реплики
Попытка форсировать ответ модели отправкой сообщения `realtimeInput: { audioStreamEnd: true }` при обнаружении тишины — тягчайшая ошибка.
- **Первопричина:** Сигнал `audioStreamEnd` семантически зарезервирован **строго под физическое отключение звукового устройства** (Mute или Hangup).
- **Последствия:** Приход этого сигнала в активном диалоге сталкивается с внутренним состоянием вокодера, вызывая крах стримингового контекста инференса: **`WebSocket Close 1011 (Failed to close streaming context)`**.

### 5.2. Антипаттерн инъекции пустых `clientContent: { turnComplete: true }`
Попытка ускорить генерацию отправкой пустого кадра `clientContent` поверх непрерывного аудиопотока разрушает темпоральные индексы KV-кэша. Модель «глохнет» и перестает воспринимать входящую речь до конца сессии.

### 5.3. Аудиомьютекс при исполнении инструментов (Защита от ошибки 1008)
Когда модель выполняет генерацию вызова функции `toolCall`, внутренний конвейер сессии блокируется в ожидании кадра `toolResponse`. Если клиент в этот момент продолжает передавать аудиосэмплы микрофона в сокет, шлюз Google фиксирует нарушение протокола: **`WebSocket Close 1008 Policy Violation: Operation is not implemented`**.
- **Инвариант:** Клиентский контроллер обязан иметь **программный аудиомьютекс**, приостанавливающий отправку микрофонных чанков в сокет на всем интервале от получения `toolCall` до отправки кадра `toolResponse`.

## 6. Сводная матрица правил акустического контекста

| Событие / Сценарий | ❌ Как НЕЛЬЗЯ делать (Антипаттерн) | ✅ Как ОБЯЗАТЕЛЬНО делать (SOTA 2026) |
| :--- | :--- | :--- |
| **Эндпоинтинг речи** | Отправлять `audioStreamEnd: true` в паузах | Доверять сквозному облачному VAD с калибровкой `silenceDurationMs: 500` |
| **Окончание ответа** | Зажигать «Слушаю» сразу по приходу `turnComplete` | Выдерживать физический интервал опустошения ЦАП $T_{\text{drain}}$ (200–500 мс) |
| **Перебивание (Barge-In)** | Игнорировать обрезание контекста сервером | Учитывать, что фраза модели в KV-кэше обрезана до точки прерывания |
| **Выполнение инструментов** | Продолжать непрерывно транслировать микрофон | Блокировать передачу чанков микрофона программным мьютексом до возврата `toolResponse` |
| **Формат аудиопотока** | Передавать стерео или заголовки WAV в чанках | Передавать исключительно сырой линейный PCM 16 кГц, моно, 16 бит Little-Endian |
