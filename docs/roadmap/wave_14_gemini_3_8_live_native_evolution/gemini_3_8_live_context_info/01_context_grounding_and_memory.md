## 1. Анатомия контекстного окна в Gemini 3.8 Live API

В отличие от стандартного REST API (`generateContent`), где контекст формируется дискретными массивами текста, в полнодуплексном протоколе `BidiGenerateContent` контекст непрерывен, гетерогенен и мультимодален.

Общий объем контекстного окна моделей `gemini-3.8-live` и `gemini-3.8-live-extended-thinking` составляет **128 000 токенов**.

```
+-----------------------------------------------------------------------------------------+
|                                  АКТИВНЫЙ KV-КЭШ (128k)                                  |
+----------------------------------+------------------------------------------------------+
| Аппаратно закрепленный префикс   | Скользящее динамическое окно (Sliding Window)        |
| (НЕ вымывается никогда)          | (Циклически вытесняется по FIFO по мере заполнения)    |
+----------------------------------+------------------------------------------------------+
| • setup.systemInstruction        | • turns[] (реплики пользователя и ассистента)        |
| • prefixTurns (иммутабельные)    | • Потоковые токены входящего аудио (PCM 16 кГц)       |
| • Декларации инструментов (tools)| • Потоковые токены синтеза модели (PCM 24 кГц)        |
| • Векторы неявного кэширования   | • Interleaved CoT (внутренние токены мышления)        |
|                                  | • toolResponse и временные снимки состояния          |
+----------------------------------+------------------------------------------------------+
```

### 1.1. Мультимодальный состав и скорость выгорания токенов

1. **Акустический битрейт токенов:**  
   Непрерывная трансляция несжатого аудио (PCM 16 кГц, 16 бит моно, $\approx 256\text{ кбит/с}$) генерирует приблизительно **20–35 аудиотокенов в секунду** (~1 200–2 100 токенов в минуту). Десять минут непрерывного разговора утилизируют от 15 000 до 25 000 токенов исключительно на кодирование звукового тракта.
2. **Токены скрытых рассуждений (Interleaved Chain-of-Thought):**  
   Модель `gemini-3.8-live-extended-thinking` генерирует промежуточные токены рассуждений перед речевым выводом. При конфигурации `thinkingLevel: "high"` глубокие рассуждения расходуют от 500 до 2 000 токенов на каждую сложную реплику.
3. **Финансовые лимиты скорости расхода (Spend-Based Velocity):**  
   На платных аккаунтах Google Cloud действуют жесткие 10-минутные лимиты расходов (Tier 1: $10 за 10 мин; Tier 2: $50 за 10 мин). Неконтролируемое раздувание контекста приводит к преждевременному разрыву соединения шлюзом Google задолго до исчерпания физических 128k токенов.

### 1.2. Механика скользящего сжатия окна (`SlidingWindow Compression`)

Когда суммарный объем данных приближается к порогу активного окна внимания, инфраструктура Google Cloud на TPU v5e/v6e выполняет циклическое вытеснение самых старых блоков данных по алгоритму FIFO.

> [!IMPORTANT]
> **Аппаратный инвариант префикса:**  
> Все структуры, переданные в поле `setup.systemInstruction`, а также декларации `setup.tools`, аппаратно закрепляются в нулевом блоке KV-кэша. Они **никогда не подвергаются сжатию или вытеснению** независимо от длительности сессии.  
> Напротив, любые данные (включая текст и кодовую базу), переданные через канал реплик `clientContent.turns`, помещаются в скользящее окно и **гарантированно вымываются через 10–15 минут активного речевого диалога**.

## 2. Сравнительный анализ 4 стратегий заземления кодовых баз

При интеграции технического контекста (исходный код, AST-деревья, конфигурации) объемом от 3 000 до 15 000 токенов существуют четыре архитектурных подхода:

| Параметр оценки | 1. Инъекция в `systemInstruction` (SOTA) | 2. Посев через `clientContent.turns` (Антипаттерн) | 3. Явный кэш `cachedContent` | 4. Динамические инструменты (`NON_BLOCKING`) |
| :--- | :--- | :--- | :--- | :--- |
| **TTFA первого ответа (Turn 0)** | 1600 – 2050 мс | 1300 – 1500 мс | 1200 – 1400 мс | 1150 – 1300 мс (заполнитель) |
| **TTFA последующих ходов** | **1100 – 1300 мс (стабильно)** | 1100 – 1400 мс (деградирует) | 1100 – 1300 мс | 1500 – 2500 мс (при чтении) |
| **Устойчивость к вытеснению (`SlidingWindow`)** | **Абсолютная (префикс зафиксирован)** | **Нулевая (вымывается за 10–15 мин)** | **Высокая (пока жив TTL)** | **Высокая (on-demand загрузка)** |
| **Риск протокольного сбоя (1011 / 1008)** | **Минимальный (статический контракт)** | **Критический (гонки буфера и VAD)** | Средний (ошибки валидации) | Средний (таймауты tool-ответов) |
| **Полнота владения контекстом** | Полная мгновенная видимость | Полная до момента вымывания | Полная мгновенная видимость | Фрагментарная (зависит от модели) |
| **Минимальный аппаратный порог**| Отсутствует | Отсутствует | **32 768 токенов (жесткий лимит)**| Отсутствует |

### 2.1. Стратегия 1: Статическая инъекция в `setup.systemInstruction.parts` (Канонический стандарт)

Кодовая база сериализуется в строгий XML-манифест с экранированием блоков `CDATA` и передается в стартовом сообщении `BidiGenerateContentSetup`.

```xml
<workspace_context>
  <file path="src/auth/SecurityService.java">
  <![CDATA[
  package src.auth;
  public class SecurityService {
      // Исходный код без искажений синтаксиса
  }
  ]]>
  </file>
</workspace_context>
```

#### Математическая модель задержки первого аудио (TTFA):
Время отдачи первого аудиопакета ($T_{\text{TTFA}}$) определяется выражением:
$$T_{\text{TTFA}} = T_{\text{net}} + T_{\text{vad}} + T_{\text{prefill}}(N_{\text{tokens}}) + T_{\text{tts}}$$

Компонента $T_{\text{prefill}}$ масштабируется пропорционально объему входных токенов:

| Объем контекста в `systemInstruction` | $T_{\text{prefill}}$ (расчетная) | Результирующий TTFA (Turn 0) | TTFA на последующих ходах | Стоимость сессии (15 мин аудио) |
| :--- | :--- | :--- | :--- | :--- |
| **500 токенов** (минимальный каркас) | 40 – 70 мс | 1150 – 1250 мс | 1100 – 1250 мс | ~$0.35 (базовый тариф аудио) |
| **5 000 токенов** (3–4 компактных класса) | 150 – 220 мс | 1350 – 1480 мс | 1100 – 1250 мс | ~$0.48 (с учетом префикса) |
| **15 000 токенов** (полный срез репозитория) | 480 – 650 мс | 1750 – 2050 мс | 1150 – 1300 мс | ~$0.72 (с учетом префикса) |

*Вывод:* Единовременный штраф prefill в 450–700 мс на Turn 0 полностью компенсируется перманентной фиксацией контекста и стабильной скоростью (~1200 мс) на всех последующих шагах сессии.

#### Защита от переключения языкового регистра (Language Drift):
Внедрение кода на C++, Java или Go создает мощный вектор смещения латентного внимания модели в сторону англоязычного программного синтаксиса.  
*Правило:* В системной инструкции обязательно должно присутствовать жесткое операционное разделение:
```markdown
[ПРАВИЛО РЕЧЕВОГО РЕГИСТРА]
Ты ведешь диалог строго на русском языке. Исходный код в блоке <workspace_context>
является справочным контекстом. Запрещено отвечать на английском языке или
зачитывать код дословно; обсуждай только архитектуру, ошибки и алгоритмы.
```

### 2.2. Стратегия 2: Посев через `clientContent.turns` (Анатомия катастрофы)

Попытка отправить кодовую базу или историю в первом сообщении `BidiGenerateContentClientContent` после получения `setupComplete` признается архитектурным антипаттерном.

#### Механизм возникновения отказов:
1. **Паразитная речь (Phantom Speech):**  
   Если клиент передает массив `turns` с ролью `user` и флагом `turnComplete: true`, сервер считает, что пользователь закончил формулировать мысль. Модель немедленно начинает зачитывать код вслух до того, как человек произнес первое слово.
2. **Костыль `initialHistoryInClientContent`:**  
   Подавление паразитной речи требует передачи флага `setup.historyConfig.initialHistoryInClientContent: true` и завершения цепочки фиктивным ходом модели `{ role: "model", parts: [{ text: "Код загружен." }] }`. Это усложняет клиентскую логику.
3. **Вымывание из скользящего окна:**  
   Через 10–12 минут файлы полностью выталкиваются новыми аудиотокенами из активного контекста внимания. Модель внезапно утрачивает знание классов, переданных на старте.
4. **Конкуренция за WebSocket-буфер (Close Code 1011):**  
   Передача тяжелого JSON (50–150 КБ) в одном сокете с непрерывным потоком PCM-аудио `realtimeInput` вызывает буферный затор. Шлюз фиксирует десинхронизацию конечного автомата и обрывает сессию с ошибкой **`1011 Internal Error`**.

### 2.3. Стратегия 3: Контекстное кэширование Gemini (`cachedContent`)

В протоколе `BidiGenerateContentSetup` присутствует поле `cachedContent: "cachedContents/xxxx"`. Однако его применение для кодовых баз объемом 3 000–15 000 токенов наталкивается на жесткое системное ограничение:

> [!WARNING]
> **Минимальный аппаратный порог (Minimum Input Token Count):**  
> Для моделей семейств Gemini 2.5 и 3.x минимальный порог создания объекта кэша через REST API `v1beta.cachedContents` составляет ровно **32 768 токенов**.  
> Попытка создания явного кэша для репозитория в 5 000–15 000 токенов отклоняется API с ошибкой валидации `400 Invalid Argument (Token count below minimum threshold)`.

*Неявное префиксное кэширование (Implicit Caching):*  
При использовании Стратегии 1 (инъекция в `systemInstruction`) аппаратные кластеры TPU v5e/v6e автоматически распознают идентичные префиксы промптов и повторно утилизируют вычисленные матрицы внимания **без явного вызова API кэширования**. Разработчик получает преимущества оптимизации латентности и биллинга бесплатно и без необходимости поддерживать TTL кэшированных ресурсов.

### 2.4. Стратегия 4: Динамическое неблокирующее извлечение (`behavior: NON_BLOCKING`)

В системный промпт помещается только оглавление проекта (дерево каталогов и интерфейсы до 1 000 токенов), а файлы подгружаются по требованию через инструмент `read_file(filePath)`.

* **Преимущества:** Минимальный начальный TTFA (1150–1300 мс) и речевые заполнители пауз («Сейчас открою сервис авторизации...»).
* **Риски:** Стохастические пропуски. При общих архитектурных вопросах модель может не догадаться вызвать инструмент и начнет галлюцинировать общими фразами.

## 3. Рекомендуемый производственный стандарт: Гибридное заземление

Целевая архитектура для производственных систем парного программирования и технических интервью:

```
+---------------------------------------------------------------------------------+
|                        ГИБРИДНАЯ АРХИТЕКТУРА ЗАЗЕМЛЕНИЯ                         |
+---------------------------------------------------------------------------------+
| 1. ЯДРО СИСТЕМЫ (3 000 – 12 000 токенов) -> setup.systemInstruction.parts       |
|    • Ключевые сущности, архитектурный каркас, интерфейсы, манифест XML CDATA     |
|    • Аппаратно зафиксировано в KV-кэше, 100% защита от вымывания Sliding Window |
+---------------------------------------------------------------------------------+
| 2. ПЕРИФЕРИЙНЫЕ ФАЙЛЫ (on-demand) -> Асинхронный инструмент read_file           |
|    • Реализации сервисов, вспомогательные утилиты, алгоритмические модули       |
|    • Подгружаются динамически со строгим флагом behavior: "NON_BLOCKING"       |
+---------------------------------------------------------------------------------+
```
