## Матрица разрешения гипотез

| ID | Проблемный вопрос / Гипотеза | Статус | Первопричина и доказанное решение (Ground Truth) |
| :--- | :--- | :--- | :--- |
| **H-01** | *«Нужен ли клиентский Silero VAD для ускорения ответа в Gemini 3.8 Live?»* | **RESOLVED (DEPRECATED)** | **Нет, категорически противопоказан.** Использование Silero VAD и отправка `audioStreamEnd: true` в активном диалоге ломает вокодер Google и вызывает WebSocket Close `1011 Internal Error` («Failed to close streaming context») либо `1008 Policy Violation` при параллельных tool calls. Gemini 3.8 Live объединяет акустический и семантический VAD в едином трансформере. Стандарт: непрерывный 16 кГц PCM с `silenceDurationMs: 500`. |
| **H-02** | *«Почему ИИ ответил невпопад на вопрос кандидата, а затем перестал отвечать?»* | **RESOLVED** | **Инъекция текстовой истории `clientContent.turns` во время аудиостриминга.** Модуль `LiveGreetingReplay` при повторном старте/реконнекте отправлял текст приветствия/истории параллельно с входящим звуком микрофона. В протоколе Bidi текстовый `clientContent` имеет абсолютный приоритет и сбрасывает аудиовнимание: модель отвечает на старый текст («невпопад»), а последующие аудиотокены рассинхронизируются, блокируя ответы. Решение: полный отказ от повторной отправки текстовых ходов; восстановление строго через `sessionResumption.handle`. |
| **H-03** | *«Является ли ошибка 1011 (с обрезанной строкой ...head to: h) исчерпанием TPM?»* | **RESOLVED** | **Нет, это маскировка аппаратным лимитом RFC 6455.** По спецификации RFC 6455 полезная нагрузка Close Frame не может превышать 125 байт (123 байта текста). Google Front End обрезает стандартный шаблон ошибки квоты ровно на 123-м байте на символе `h`. При этом GFE транслирует в код 1011 любые сбои: превышение лимита параллельных сессий (concurrent requests), зависание «фантомных сессий» при некорректном закрытии (слот висит 60–180 сек), или падение воркера gRPC `INTERNAL` из-за нарушения порядка фреймов. |
| **H-04** | *«Как заземлять контекст кода задач (3 000 – 15 000 токенов)?»* | **RESOLVED** | **Строго через `systemInstruction.parts` (XML + CDATA).** `clientContent` вымывается из памяти алгоритмом Sliding Window через 10–15 минут разговора. `cachedContent` не работает, так как минимальный порог создания кэша в API составляет 32 768 токенов. Контекст в `systemInstruction` фиксируется в префиксном KV-кэше, никогда не удаляется и ускоряется встроенным неявным кэшированием TPU. Дополнительные файлы подгружаются неблокирующим инструментом `read_file` (`behavior: "NON_BLOCKING"`). |
| **H-05** | *«Можно ли использовать Round-Robin ротацию API-ключей при реконнекте?»* | **RESOLVED** | **Нет, ключ должен быть привязан к сессии (Session-Pinned).** Токен восстановления `sessionResumptionUpdate.newHandle` криптографически привязан к конкретному проекту и API-ключу, создавшему сессию. Попытка восстановить сессию с другим ключом из пула вызывает немедленный разрыв с кодом `1011` или `1008`. |
| **H-06** | *«Нужны ли модули Dead-Air Guard и инжекция синтетической тишины?»* | **RESOLVED (DEPRECATED)** | **Нет, это деструктивный костыль.** Вброс искусственных PCM-фреймов разрушает акустические эмбеддинги языковой модели и сбивает серверный VAD. Gemini 3.8 Live штатно удерживает WebSocket с помощью TCP keepalive и поддерживает режим `proactive_audio`, не требуя искусственной активности. |
| **H-07** | *«Достаточно ли флага turnComplete: true для открытия микрофона кандидата?»* | **RESOLVED** | **Нет, необходим композитный предикат.** В моделях с рассуждениями флаг `turnComplete: true` может приходить на промежуточные речевые связки («Секунду, сверяю код...»), пока модель продолжает думать (`interactionStatus: "IN_PROGRESS"`). Переход в состояние готовности допустим строго при: `AudioBuffer == 0` (ЦАП опустошен) $\land$ `PendingTools == 0` $\land$ `interactionStatus == "IDLE"`. |

## Зафиксированные архитектурные решения (Decisions)

1. **D-01 (Purge Middleware):** Полностью демонтировать и исключить из цепочки вызовов:
   - Клиентский Silero VAD (пакеты `@silero/vad`, `onnxruntime-web` в голосовом контуре).
   - `LiveDeadAirGuard` и сторожевые таймеры синтетической тишины.
   - `LiveGreetingReplay` и отправку массивов `clientContent.turns` при восстановлении соединения.
2. **D-02 (Native Audio Engine):** Перевести аудиоподсистему браузера на Single-Sink Web Audio:
   - Микрофон: 16 кГц Mono Int16 через `AudioWorklet`, непрерывная передача в сокет.
   - Воспроизведение: 24 кГц Mono через кольцевой буфер $2^{20}$ сэмплов с тактильным спадом огибающей 5 мс (120 сэмплов) при прерывании (Barge-In) и учетом времени опустошения ЦАП ($T_{\text{drain}}$).
   - Никаких параллельных скрытых тегов `<audio>` (сохранение аппаратного AEC).
3. **D-03 (Canonical Grounding):** Кодовые манифесты передавать исключительно в `systemInstruction` в формате XML CDATA. Для динамических файлов зарегистрировать `read_file` с `behavior: "NON_BLOCKING"`.
4. **D-04 (Resumption Protocol):** Внедрить штатную обработку `sessionResumptionUpdate.newHandle`, перехват `goAway` с упреждающим открытием сокета до 10-минутного таймаута и фиксацию API-ключа за сессией в `LiteLLM_Proxy`.
5. **D-05 (Clean Teardown):** Завершать сокеты строго каноническим кадром RFC 6455 `1000 Normal Closure` с ожиданием подтверждения, исключая накопление фантомных сессий на балансировщиках Google.
