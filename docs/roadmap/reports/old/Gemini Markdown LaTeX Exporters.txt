Technical Report: Exporting Google Gemini Deep Research and Google Docs to Clean Markdown with Native LaTeX FidelityModern software engineering and scientific research workflows increasingly depend on frontier reasoning engines to generate technical design documents, systems architecture specifications, and formal literature reviews. Google Gemini Deep Research has emerged as an engine for synthesizing deep, multi-source inquiries, yet incorporating its outputs into version-controlled engineering repositories, documentation generators (such as Hugo, VitePress, and Docusaurus), and local-first knowledge bases (such as Obsidian) remains difficult.The technical breakdown occurs at the interface between the web browser, the Google Docs document model, and plain-text markup formats. Exporting long-form reports containing heavy mathematical notation, complex tabular data, and academic citations routinely results in corrupted structural layouts, flattened text blocks, or equations converted into uneditable rasterized images. Resolving these issues requires an analysis of DOM tree representations, OpenXML document models, and modern parsing architectures.Document Serialization Failures in AI Research Ingestion PipelinesThe breakdown in document fidelity when moving content from Gemini Deep Research to Markdown stems from architectural differences across three format transformations: the Gemini web client Document Object Model (DOM), the Google Docs internal representation, and operating system clipboard serializers.Gemini Deep Research outputs do not exist as static Markdown files on the client side; they are dynamically rendered into an Angular-based web application interface. Mathematical expressions are rendered using KaTeX to generate mathematical typography via HTML spans and embedded MathML structures. The rendered KaTeX block typically encapsulates two internal representations: an accessible MathML block (.katex-mathml) that contains an `` element preserving the original LaTeX syntax, and an visual layer (.katex-html) consisting of nested spans positioned with explicit CSS sizing, struts, and font transformations. In addition, Gemini often attaches a `data-math` attribute to wrapping containers.When an engineer copies a report using the native "Copy content" button in the Gemini web interface, the application relies on an internal DOM text serializer rather than returning the raw text string returned by the model. This serializer traverses the rendered layout and discards semantic block boundaries, heading hierarchies (#, ##, ###), and soft line breaks. The resulting plain-text clipboard buffer collapses multi-page technical analyses into an unsegmented block of text, stripping GitHub Flavored Markdown (GFM) tables of their pipe alignments and row structures.A secondary failure occurs when users bypass clipboard operations using Gemini's native "Export to Google Docs" integration. Google Docs does not use Markdown or native LaTeX internally. Instead, it maps imported mathematical expressions into its proprietary Equation editor format or static vector/drawing structures.When the user attempts to download this Google Doc as a Markdown archive (File > Download > Markdown (.md)), the export engine cannot translate these internal equations into standard TeX math syntax. The engine falls back to rasterization: every inline and display equation is converted into a PNG image and embedded within the Markdown document as a reference link paired with a Base64 data string.A report containing dozens of mathematical derivations can balloon from 40 kilobytes of text into several megabytes of binary data, creating repository bloat and rendering mathematical equations unsearchable, non-editable, and poorly scaled on high-resolution displays. Gemini Deep Research also injects proprietary citation tokens, such as [cite_start] and, directly into the layout tree, which disrupt downstream Markdown parsers if they are not transformed into standard footnotes or references.Comparative Assessment of Export and Ingestion ArchitecturesThe software ecosystem offers several utilities designed to address these serialization bottlenecks, ranging from in-browser DOM traversers and RPC interceptors to command-line document transformation pipelines.Solution NameArchitecture TypeStar Metric / Maintenance StateFormula Fidelity (LaTeX / KaTeX)GFM Table PreservationExecution Context / Data PrivacySoftware LicenseCore Architectural BottleneckVoyager (Nagi-ovo/voyager)Browser Extension (Chromium, Edge, Safari)20,000+ Stars; However, this script is designed for standard chat conversations; because Gemini Deep Research streams long-form reports through asynchronous background endpoints and detached state machines, the script often fails to capture the full report.The Google Docs Conversion PathWhen a report is exported directly to Google Docs, Workspace Add-ons like GD2md-html (Docs to Markdown) fail to solve the equation rasterization problem. The Google Apps Script Document API lacks native methods to read the TeX math backing its Equation elements. Consequently, GD2md-html skips these equations, inserting warning flags in the output text instead of mathematical markup:The standard approach for converting equation-dense Google Docs into clean Markdown relies on an intermediate conversion through Microsoft Word's OpenXML container (.docx). When Google Docs exports to .docx, it translates internal equations into Office Math Markup Language (OMML) using `` XML tags rather than flattening them to images.Pandoc's native .docx reader can parse this OMML syntax and convert it into TeX math. Using Pandoc with the --from=docx --to=gfm+tex_math_dollars options converts these formulas into native inline $ ... \( and display \)\(...\)$ delimiters, retains GFM table structures, and saves embedded diagrams to a local assets directory instead of embedding large Base64 strings.Universal Clipboard and Parser LibrariesLocal-first web clippers and markdown transformation engines provide a flexible alternative for parsing clipboard contents. Defuddle, the extraction engine built for the Obsidian Web Clipper, strips boilerplate code, navigation frames, and tracking scripts from web pages. However, Defuddle is designed for standard web articles and lacks built-in rules for resolving KaTeX DOM subtrees. Running Defuddle against raw Gemini HTML often extracts unformatted MathML strings or drops formulas altogether.Reliable HTML-to-Markdown conversion requires using the turndown engine paired with turndown-plugin-gfm and custom AST rules. By writing rules that target KaTeX DOM elements, developers can extract the contents of the `` tag, discard visual formatting spans, and wrap the formula in standard LaTeX math delimiters.JavaScriptimport TurndownService from 'turndown';
import { gfm } from 'turndown-plugin-gfm';

const turndownService = new TurndownService({
  headingStyle: 'atx',
  codeBlockStyle: 'fenced'
});

turndownService.use(gfm);

// Custom extraction rule for KaTeX math structures
turndownService.addRule('katex-parser', {
  filter: (node) => {
    return node.classList && (
      node.classList.contains('katex') || 
      node.classList.contains('math-inline') || 
      node.classList.contains('katex-display')
    );
  },
  replacement: (content, node) => {
    const texAnnotation = node.querySelector('annotation[encoding="application/x-tex"]');
    if (texAnnotation) {
      const tex = texAnnotation.textContent.trim();
      const isDisplay = node.classList.contains('katex-display') || node.tagName.toLowerCase() === 'div';
      return isDisplay ? `\n\n
$$${tex}$$\n\n:$\({tex}\)`;
}
const dataMath = node.getAttribute('data-math');
if (dataMath) {
return `$${dataMath.trim()}$`;
}
return content;
}

This approach uses the Google Drive API to download the file as a .docx container, then processes the OMML math with Pandoc.Bash#!/usr/bin/env bash
set -euo pipefail

# Ingestion script: Converts a Google Doc containing Gemini research to clean GFM
# Usage: ./ingest-doc.sh  

DOC_ID="$1"
TARGET_NAME="$2"

echo "Extracting document ${DOC_ID} via Google Drive API..."

# Request .docx export to preserve OMML equation structures
curl -s -L \
  -H "Authorization: Bearer $(gcloud auth application-default print-access-token)" \
  "https://www.googleapis.com/drive/v3/files/${DOC_ID}/export?mimeType=application/vnd.openxmlformats-officedocument.wordprocessingml.document" \
  -o "${TARGET_NAME}.docx"

echo "Executing Pandoc AST transformation..."

# Convert OMML math directly to LaTeX math delimiters in GFM
pandoc "${TARGET_NAME}.docx" \
  --from=docx \
  --to=gfm+tex_math_dollars \
  --extract-media="./assets/${TARGET_NAME}" \
  --wrap=none \
  -o "${TARGET_NAME}.md"

rm "${TARGET_NAME}.docx"
echo "Transformation complete: ${TARGET_NAME}.md"
This headless pipeline solves the image rasterization problem. Formulas parse directly into $ ... \( and \)\(...\)$ delimiters, GFM table structures remain intact, and actual embedded diagrams are saved to a separate assets folder rather than serialized as Base64 strings.Gap Analysis and Technical BottlenecksWhile tools like Voyager and the Pandoc pipeline address the primary export issues, several edge cases persist across AI-generated technical reports:DOM Selector VolatilityExtensions that depend on client-side scraping are vulnerable to changes in Google's frontend code. The Gemini web client uses minified, dynamic class names and updates its Angular Material component hierarchies regularly.For example, an update to Gemini's sharing UI altered the [data-test-id="share-button-tooltip-container"] selector, which temporarily prevented Voyager from mounting its export options in the menu. Exporters that rely on DOM scraping require regular updates to keep their selectors aligned with the web client.Pipe Character Collisions in GFM TablesA recurring issue in mathematical reports involves using the vertical bar (|) within LaTeX expressions placed inside Markdown tables. The pipe character is standard LaTeX notation for determinants, absolute values ($\vert{}x\vert{}$), evaluations, and conditional probabilities ($P(A\vert{}B)$).However, GitHub Flavored Markdown uses the pipe as its column delimiter. If an exporter extracts raw LaTeX strings into a GFM table cell without sanitization, downstream Markdown parsers interpret the equation's internal pipe characters as cell dividers, corrupting the table layout. Standard export tools often fail to catch this collision, which requires converting raw pipes inside table cells into \vert, \mid, or escaped characters (\|).Citation Ingestion and Footnote TranslationGemini Deep Research outputs incorporate interactive citation chips linked to search results, styled as [cite: source_id] or [cite_start]. The available export tools handle these markers inconsistently:AI Chat Exporter uses regular expressions to strip citation tags entirely, removing the internal markers but discarding the reference links in the process.Voyager includes configuration options to either remove the markers or preserve them as raw text.No single tool currently parses these citation chips into standard GFM Markdown footnotes (e.g., [^1]) matched to a consolidated bibliography at the bottom of the document, which requires manual post-processing for academic and technical publications.Engineering Recommendations: Build versus Adopt EvaluationEngineering organizations should decide whether to adopt existing tooling or build a custom utility based on their primary operating environment and automation requirements.When evaluating team workflows, the deciding factor is whether documents are processed interactively or through automated pipelines:For interactive, browser-based research, teams should adopt Voyager (Nagi-ovo/voyager). It provides a fast, one-click export experience directly within the Gemini interface. It extracts LaTeX from KaTeX structures and formats tables without requiring auxiliary CLI tools, making it the most practical choice for individual researchers, developers, and technical writers.For automated publishing, knowledge-base indexing, and CI/CD pipelines, teams should adopt the Google Docs -> DOCX -> Pandoc Pipeline. This workflow eliminates dependency on the browser DOM by pulling .docx files through the Google Drive API and converting OMML formulas into LaTeX via Pandoc. It is reliable, handles large document collections, and integrates cleanly into automated continuous delivery setups.Teams should consider building a custom micro-utility only if they have specialized ingestion requirements that existing tools do not address. Such requirements typically include converting internal citation chips into GFM footnotes ([^1]: URL), escaping pipe characters within table-bound math formulas, or pushing cleaned reports directly into internal APIs.Teams that choose to build a custom solution can do so with a small, maintainable codebase. Rather than writing a full browser extension or DOM parser from scratch, developers can create a lightweight user script or local ingestion server using turndown and turndown-plugin-gfm, combined with targeted extraction rules for KaTeX `` elements and Gemini citation tags.By selecting the appropriate tool for their operational context—Voyager for interactive browser use, Pandoc for automated backend workflows, or a targeted Turndown parser for custom pipelines—engineering teams can export Gemini Deep Research reports into clean Markdown with fully editable mathematical notation, intact tabular data, and consistent formatting.
